# Agent AP1.0: design, parity and cost estimate

[Back to the README](../README.md) · [frozen workflow WP1.1](wp11_freeze.md) · [plan](prepay_plan.md) · [process](process.md) · code: `src/ap10.py`, `eval/ap10_parity.py`, `tests/test_ap10.py`

The agent is the second design for the same job: instead of code fixing the order of steps (a workflow), a language model chooses the steps within caps. AP1.0 mirrors the frozen workflow WP1.1 in its tools. **Nothing in it has been run with a model: this page is built from free runs only.**

## Design
Day by day, the model is shown the day's top 15 candidate claims by the workflow's score, each with the workflow's dollar estimate and its advice, PEND or PAY. Tools: `provider_history` (a clinician's earlier counts), `pend` (request charts for claims, within the daily cap of 10, one call for all), `read_chart` (the office's answers and the level the rules would pay), `adjust` (pay a pended claim at another level or deny it, instead of the rule's level) and `done`. A claim the model leaves alone is paid as billed; a pended claim it does not adjust is resolved by the same rules as the workflow. The model is consulted only on days where the workflow advises at least one pend (all other days pay as billed with no call). Costs: a per-run dollar cap is required (`llm_agent` refuses to start without one or without `ANTHROPIC_API_KEY`) and the run stops cleanly at the cap. The answer key is never visible to the agent (`tests/test_wp10.py` checks the module).

## Parity (scripted agent, development seeds, free)
A scripted agent that always follows the advice reproduces the workflow's decisions exactly on three P-DEV2 select seeds (8001, 8042, 8083): the same claims pended at the same levels, 100% match (`tests/test_ap10.py` checks the same on a built dataset). So any difference in a paid run comes from the model's choices, not from the tools.

## Cost estimate for the paid run (not yet approved)
From the scripted run's counts of model turns (four per consulted day) and an estimate of tokens per turn, **without prompt caching**, at list prices per million tokens (Sonnet 5.5 $2 in / $10 out; Haiku 5.5 $1 / $5; Opus 5.5 $4 / $20). There is no recorded usage for a prepay agent, so this is an estimate, not a measurement; the real bill is checked in the Console.

| Model | Per seed | Ten test seeds | With about 40% saving from caching the system prompt and day prefix |
|---|---|---|---|
| Sonnet 5.5 | about $3.8 | about $38 | about $23 |
| Haiku 5.5 | about $1.9 | about $19 | about $11 |
| Opus 5.5 | about $7.5 | about $75 | about $45 |

Seeds differ a lot in how many days the workflow pends on (54 to 225 consulted days in the three checked), so ten seeds could cost half or 1.5 times the mean. **Proposed cap: $45 for the release with Sonnet 5.5 on ten test seeds** (P-TEST j = 0 to 9, seeds 6001 to 6370), per-seed cap $6, plus optionally **$5 for a one-seed smoke run on a development seed** first. Needs from Simmy: approval of the cap, and an `ANTHROPIC_API_KEY` in `.env` (there is none in this checkout).

## What the true test would compare (step 6, one run)
The frozen workflow WP1.1, the previous workflow WP1.0 and the controls (free) and the agent AP1.0 (paid) on P-TEST j = 0 to 9, once. The agent against the workflow, and the workflow against the tuned edit and WP1.0. The seeds are unread; the registry shows them as fresh.
